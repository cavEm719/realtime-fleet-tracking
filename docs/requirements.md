# 需求文档（完整版）

本文档给 main 分支的完整版补上需求，用来回答两个问题：每个设计是为了满足哪条需求；哪些设计没有对应的需求，或者和别的设计重复。

规模数字是对一个中等规模 SaaS 的假设，不是真实客户统计。项目在先实现、后写需求，所以第 6、7 节是用需求回头检查已有设计，不是按需求推导出的设计过程。

第 6 节最初为 AI 助手改写而列出的"待实现"设计，均已实现并验证（ADR 037–045）。

## 1. 系统和用户

物流公司（租户）把船舶位置持续上报给系统。公司员工在网页上实时查看本公司船队的位置，船舶进港、离港时自动生成记录并推送；运营人员也可以用自然语言向 AI 助手提问。多家公司共用一套系统，每家公司只能看到自己的数据。

| 使用者 | 做什么 |
|---|---|
| 调度员、运营人员 | 实时查看船队位置和进出港记录，向 AI 助手提问 |
| 公司管理员 | 维护本公司关注的港口 |
| 位置数据发送方 | 成批上报船舶位置 |

## 2. 规模假设

| 项目 | 假设值 |
|---|---|
| 公司数 | 50 家 |
| 每家公司船舶数 | 100–500 艘 |
| 位置上报间隔 | 航行中约 10 秒一次 |
| 每家公司同时在线人数 | 50 人 |
| 每家公司关注的港口数 | 不超过 20 个（物流公司只关心自己航线上的港口） |
| 港口修改频率 | 很少，平均每家公司每月几次 |
| AI 提问量 | 每家公司每分钟最多 100 次 |

由此推出：

| 推导量 | 计算 | 结果 |
|---|---|---|
| 平均位置输入 | 50 家 × 平均 300 艘 ÷ 10 秒 | 约 1,500 条/秒 |
| 峰值位置输入 | 全部公司按 500 艘计 | **约 2,500 条/秒** |
| 单家公司最大输入 | 500 艘 ÷ 10 秒 | 50 条/秒 |
| 同时在线连接 | 50 家 × 50 人 | **2,500 个** |
| 位置推送量（不合并） | 2,500 条/秒 × 每家 50 人 | 约 12.5 万次/秒 |
| 位置推送量（每 100 ms 合并成一帧） | 2,500 个连接 × 每秒 10 帧 | 约 2.5 万帧/秒 |
| 进出港距离计算 | 2,500 条/秒 × 每家最多 20 个港口 | 约 5 万次/秒 |
| AI 峰值提问量 | 50 家 × 100 次 ÷ 60 秒 | **约 83 次/秒** |
| 同时等待模型回答的请求 | 83 次/秒 × 每次约 4 秒 | **约 330 个** |
| AI 调用 Java API 的次数 | 83 次/秒 × 每问最多 8 次工具调用 | 最多约 670 次/秒 |

每条位置只需要和本公司的港口逐个计算距离。每秒约 5 万次距离计算对 CPU 可以忽略，所以不需要先用空间索引筛选港口；只有当一家公司要监控成千上万个港口或区域时才需要。

每分钟 100 次是防止突发和滥用的上限，不是平均用量。按每个问题约 0.001–0.005 美元估算，全部公司全天按上限提问时每天会花费数千到数万美元，实际额度应结合成本预算设定。

## 3. 功能需求

### F1 位置接入
- F1.1 发送方按公司成批上报位置；系统只接受本公司的船舶。
- F1.2 一艘船第一次上报时归入上报它的公司，之后不能被其他公司接管。
- F1.3 同一条位置重复上报、整批重发时，结果和只发一次相同。
- F1.4 晚到的旧位置不能覆盖已有的新位置，船的位置不能倒退。
- F1.5 系统确认接收成功后，这批位置最终一定会被处理，不能因为服务重启而丢失。

### F2 进出港识别
- F2.1 每个港口有较小的进港范围和较大的离港范围，船在两者之间漂移不改变状态。
- F2.2 连续若干个点（默认 3 个）满足条件、且持续一段时间（默认 2 分钟）后，才确认一次进港或离港。
- F2.3 同一次进港或离港只记录一条，服务崩溃、重启或重复处理都不能产生第二条。
- F2.4 船的状态更新和进出港记录必须同时生效或同时不生效。
- F2.5 管理员可以新建、修改、删除本公司的港口；修改不回算历史记录，删除后历史记录保留。

### F3 实时推送
- F3.1 员工打开页面后，可以订阅本公司全部船舶，也可以只订阅指定船舶。
- F3.2 推送的都是已经保存生效的数据。
- F3.3 船的位置只需要显示最新的，中间位置可以合并或丢弃；进出港记录不能合并，也不能丢。
- F3.4 一个连接网络慢或不读数据，只断开这一个连接，其他人照常接收。
- F3.5 断线重连后，可以补回断线期间的进出港记录，补回的记录不和已收到的重复。

### F4 多租户
- F4.1 所有查询、推送和 AI 回答只包含本公司的数据。
- F4.2 每家公司有自己的上报额度和 AI 提问额度；超出时只拒绝这家公司，其他公司不受影响。额度在所有实例间统一计算。

### F5 AI 运营助手
- F5.1 支持中英文提问：查船舶状态和位置、查某段时间的进出港记录、按港口或日期统计、查某个位置附近的船舶。
- F5.2 公司身份由服务端决定，模型无法通过参数或提问内容改变它。
- F5.3 模型不能直接写 SQL，只能把船名、港口名换成编号后填写固定格式的查询规格，由程序校验后执行，并记录实际执行的查询（执行回执）。
- F5.4 每个回答附带由程序生成的查询条件和结果表格，供用户核对。
- F5.5 工具返回的时间使用 ISO 格式的 UTC 时间，不让模型换算毫秒时间戳。
- F5.6 船名或港口名有歧义、找不到时，先请用户澄清，不自行选择。
- F5.7 数据暂时不可用时如实告知，不编造结果。
- F5.8 支持追问：同一对话中的后续问题可以引用前面的内容，不管请求被分到哪个 AI 服务实例。对话 30 分钟无新消息后自动清除，每个对话保存的轮数有上限。
- F5.9 AI 只能读取数据，不能修改任何数据。

## 4. 非功能需求

### N1 容量
- N1.1 持续接收峰值 2,500 条/秒的位置输入。
- N1.2 同时维持 2,500 个在线连接，其中每家公司 50 个。

### N2 延迟
- N2.1 从系统收到位置到员工页面收到更新，99% 在 2 秒内。
- N2.2 进出港记录从确认到推送，99% 在 2 秒内。

### N3 可靠性
- N3.1 已确认接收的位置和已确认的进出港记录不能丢失（F1.5、F2.3）。
- N3.2 处理服务或数据库短暂故障时，可以暂停处理，但不能拒绝或丢弃已确认接收的位置；恢复后继续处理。

### N4 可用性
- N4.1 每个服务至少部署两个实例，坏掉一个时服务不中断。
- N4.2 发布新版本时逐个实例更新，不停机。
- N4.3 AI 助手故障或变慢，不能影响位置接入、进出港识别和推送。

AI 助手依赖外部大模型，是系统里最慢、最不稳定的功能。如果它和位置追踪在同一个进程里，会通过共用的资源拖垮主流程：

| 共用资源 | AI 出问题时的影响 | 不拆服务能否解决 |
|---|---|---|
| 处理请求的线程 | 模型变慢时，每个提问最长占用线程 30 秒，线程被占满后位置上报只能排队或超时 | 能：给 AI 单独的线程池，并限流 |
| 数据库连接 | AI 的统计查询长时间占用连接，位置处理拿不到连接 | 能：给 AI 单独的连接池，并设置查询超时 |
| 内存 | 模型结果和对话历史耗尽内存，整个进程被终止，位置追踪随之中断 | 不能：同一进程只有一份内存，崩溃时一起停止 |
| 启动和发布 | AI 的提示词和工具需要频繁调整，每次发布都要重启整个进程，断开所有 WebSocket 连接；AI 配置错误还会导致整个应用无法启动 | 不能：同一进程只能一起启动、一起发布 |

前两项可以在同一进程内做资源隔离；后两项只有拆成独立服务才能隔离。因此 AI 助手作为独立服务部署。

### N5 港口修改生效时间
- N5.1 港口修改后 1 分钟内对新位置生效即可，不要求立即生效。修改或删除后的 1 分钟内，系统仍可能按旧范围产生进出港记录，包括已删除的港口，这在业务上可以接受。

### N6 AI 助手
- N6.1 每个问题 30 秒内给出回答或明确的失败提示；每个问题最多调用 8 次工具。
- N6.2 每家公司每分钟最多 100 次提问。
- N6.3 AI 服务能同时处理约 330 个等待模型回答的请求。
- N6.4 模型服务故障或限流时，快速返回失败，不能让大量请求一起重试、放大故障。
- N6.5 AI 的数据查询在 MySQL 只读副本上执行，不占用主库；只读副本故障时直接告知用户"暂时无法查询"，不改查主库。
- N6.6 每个回答标注"进出港数据截至某时（UTC）"。这个时间来自主库每秒写入、经复制到达副本的心跳时间。船舶最新位置来自 Redis，是实时数据，不受复制延迟影响。
- N6.7 副本落后主库超过 60 秒时，视同副本不可用，告知用户"数据同步延迟，暂时无法查询"。

## 5. 不在范围内

- 登录认证：公司编号由请求传入，系统保证按公司编号隔离数据，但不能防止冒用编号。
- 船舶历史轨迹：只保存最新位置和进出港记录。
- 告警规则：起草、确认和通知都不做。
- 前端页面。
- Kafka、Redis、MySQL 自身的高可用部署（见 7.3）。

## 7. 检查结果

### 7.1 多余的设计

逐项核对 main 的代码后，只有下面几项在当前需求下确实多余：

| 设计 | 为什么多余 | 删掉后功能怎样保证 |
|---|---|---|
| 港口网格索引 | 网格按公司划分，每家公司不超过 20 个港口，逐个计算距离就够 | 每家公司一份港口列表，逐个计算；港口更新时仍整体替换列表（写时复制），处理线程读取时不加锁 |
| 港口编辑时加共享锁并拒绝旧版本 | 防止"港口刚修改或删除，处理线程还按旧范围确认了一次进出港"。N5.1 允许修改后 1 分钟内按旧范围判断，这种情况在需求允许的范围内 | 变更通知加 60 秒对账，1 分钟内所有处理实例都换成新范围 |
| 调用内部 API 的重试、熔断和公司配置过期缓存 | 只属于已删除的 Java AI 服务 | 随 Java AI 服务一起删除；熔断只在调用外部模型时需要（N6.4） |
| 处理服务和 API 的虚拟线程 | 处理服务由固定的 Kafka 消费线程处理，API 的请求量用普通线程池就够 | 改回普通线程池 |
| 链路追踪（包括写进发件箱的追踪信息） | 不设可观测性需求 | 保留日志、健康检查和 Prometheus 指标 |

以上各项均决定删除。另外，订阅表的 64 分片（见 7.2）简化为 ConcurrentHashMap 的按键原子更新。

### 7.2 曾被认为多余、核对后不是

| 设计 | 之前的判断 | 核对结果 |
|---|---|---|
| 网关的事件 ID 去重 | 时间戳检查已能挡住重复事件，ID 去重多余 | **不多余**。断线重连时会新建会话，时间戳记录是空的，而且代码有意不在补发时恢复时间戳（较早发生但较晚提交的事件仍要送达）。这时只有用客户端确认过的事件 ID 预先填入去重表，才能避免把客户端已有的事件再发一遍 |
| 网关的虚拟线程 | 2,500 个连接用普通线程池就够 | **不多余**。每个连接有自己的发送任务，慢客户端会让它的发送任务一直阻塞。用虚拟线程时，再多的慢客户端也只是挂起很轻的虚拟线程；用普通线程池时，慢客户端一多就会占满线程，未收录在本仓库的单进程简化实验改用有上限的普通线程池后，压测中出现了正常连接被断开（很可能是这个原因，但未最终确认） |
| 断线续传协议 | 和"往前多取一段 + 客户端按 ID 去重"重复 | **不是重复，是由谁负责的选择**。完整版在服务端完成去重和排序，任何客户端连上都能得到不重不漏的结果；简单做法把这件事交给每个客户端自己实现。项目没有前端，服务端实现能直接测试 F3.5。可以简化，但不属于重复保障 |
| Redis GEO | 每条位置都写 GEO，只为偶尔的"附近的船"查询 | **两种做法都满足需求，是取舍**。GEO 把成本放在写入（约 2,500 次/秒，对 Redis 很小），遍历最新位置把成本放在查询（AI 每秒最多约 83 次提问）。都不是瓶颈，可留可删 |
| 订阅表 64 分片 | 有了不可变集合以后，分片不起作用 | **部分正确**。读取确实不加锁；但更新不可变集合时仍要加锁，防止两个连接同时订阅同一艘船时丢掉一个。分片的作用是分散这把锁。改用 ConcurrentHashMap 的按键原子更新，可以用更少的代码达到同样效果，属于可以简化，而不是多余。另外，订阅全部船舶走的是另一把锁，没有分片 |
| 事件 INSERT IGNORE | 和状态条件更新重复 | 是成本很低的兜底，保留 |
